# Life 家庭生活工作台

## 技术路线评审 v0.1

> 状态：首轮架构建议，供数据库路线、部署路线和研发拆分评审。
>
> 业务基线：[PRD v0.10](./Life-家庭生活工作台-PRD-v0.10.md)。本文件不改变 PRD 已确认的业务范围，只将其转译为可实现的技术边界。

## 1. 评审结论

首期采用“移动端 PWA + TypeScript 模块化单体 API + PostgreSQL + 私有对象存储 + PostgreSQL 任务队列 + 家庭级 AI 网关”的路线。

推荐部署形态：

```text
腾讯云轻量服务器
├── Caddy / HTTPS 反向代理
├── Life Web/API 容器
├── Life Worker 容器
└── PostgreSQL 容器或同机 PostgreSQL 服务

腾讯云配套能力
├── COS 私有存储：原始账单、媒体、HowToCook 快照和发布包
├── KMS/Secrets Manager：家庭 AI API 密钥引用与加密材料
└── COS/异地备份：数据库备份和恢复副本
```

首期不拆微服务、不建设桌面端、不引入独立 Redis、不引入独立向量数据库、不让运行时依赖 GitHub 在线访问。

## 2. 已确认事实、技术假设和风险

### 2.1 已确认事实

| 项目 | 结论 |
|---|---|
| 终端 | 只做移动端 PWA / 移动 Web，优先 390–430px |
| 部署 | 首发部署在用户自有腾讯云轻量服务器 |
| 代码 | 不继承旧 Life 代码、数据库和服务器数据，新项目初始化 |
| 数据边界 | 一个家庭是一个租户；用户只能归属于一个家庭 |
| 财务 | V1.0 首发必须完整上线，支持多来源导入、表头探测、去重关联、预算环、趋势和下钻 |
| AI | 每个家庭独立 API 连接、记忆文件、向量命名空间和审计 |
| HowToCook | 同步时下载上游最新版到本地，解析、标准化、审核后发布 |
| 保留 | 原始账单文件和导入中间数据保留 365 天；正式账本不随之删除 |

### 2.2 当前技术假设

- 首发用户规模以单台轻量服务器可承载的家庭型低并发场景为基线，不为未知规模提前拆分微服务。
- AI 服务采用家庭自己提供的 API Endpoint、协议和模型信息，V1.0 优先支持 OpenAI 兼容协议，协议适配层保留扩展点。
- 财务统计必须由确定性服务计算，AI 只能解释、匹配、提出建议，不能成为账本计算引擎。
- 财务导入文件以用户主动上传为入口，不保存银行、支付宝或微信登录凭据。
- 生产环境可以使用腾讯云 COS、KMS/Secrets Manager 等配套服务；如果账号尚未开通，应先做容量和费用确认。

### 2.3 必须在技术评审中验证的风险

1. 轻量服务器的 CPU、内存、磁盘和带宽是否同时满足 PostgreSQL、PDF/OCR、HowToCook 解析和 AI 任务的峰值。
2. 腾讯云 COS、KMS/Secrets Manager、域名和证书是否已准备，是否需要跨地域备份。
3. PostgreSQL 是否可以稳定启用 `pgvector`；如果不能，家庭记忆向量检索需要使用独立索引服务或先降级为关键词/结构化记忆检索。
4. HowToCook 最新仓库版本的许可证、图片和第三方素材是否允许本地再分发。
5. 各类银行、支付平台和记账 App 的导出文件样本是否足以覆盖多行表头、合并单元格、多 Sheet、PDF 和 ZIP。

## 3. 技术选型建议

### 3.1 移动端

| 层 | 建议 | 选择原因 |
|---|---|---|
| UI | React + TypeScript | 适合复杂表单、图表、权限状态和移动端组件化 |
| 构建 | Vite | 启动快，适合独立 PWA，不引入桌面端 SSR 负担 |
| 路由 | React Router | 路由可直接映射 PRD 页面和权限边界 |
| 服务端数据 | TanStack Query | 统一处理加载、缓存、重试、失效和请求状态 |
| 表单 | React Hook Form + Zod | 导入映射、预算、授权等表单需要同一套校验契约 |
| 图表 | 首选 Apache ECharts；保留 SVG 降级方案 | 环图、趋势线、触摸点击、tooltip 和下钻需要成熟交互能力 |
| PWA | Service Worker 只缓存静态资源 | 禁止缓存财务、AI、家庭业务 API 响应，避免串租户和旧数据泄露 |

前端不保存家庭 API 密钥，不把 `household_id` 当成权限依据，不直接拼接财务查询条件。所有图表由 API 返回“展示值 + 可下钻引用”，避免前端自行推导账务口径。

### 3.2 后端

推荐使用 Node.js 的当前 LTS 版本和 TypeScript，后端采用 Fastify 模块化单体：

```text
API 进程
├── auth
├── household / member / permission
├── family-space
├── food / recommendation / recipe
├── howtocook-import / publishing
├── finance / ledger / budget / asset
├── finance-import / mapping / reconciliation
├── ai-gateway / memory / proposal
├── media / export
└── audit / health
```

推荐配套：

- `Zod`：请求、响应、任务消息和外部解析结果校验。
- `Kysely` 或等效的类型安全 SQL 查询层：允许显式控制事务、RLS 上下文和财务 SQL，不让 ORM 隐藏租户条件。
- 版本化 SQL migration：账本、预算和关联关系需要可审查的数据库变更。
- `pg-boss` 或同类 PostgreSQL 任务队列：避免为了异步任务额外引入 Redis。
- OpenAPI：从路由契约生成接口文档和前端类型，避免 UI、API、验收口径漂移。

这里的“模块化单体”不是把所有代码写在一起，而是统一部署、统一认证、统一租户上下文，模块之间通过明确的领域服务和事件契约交互。后续若账单解析或 AI 任务负载明显增长，再把 Worker 独立扩容，不改变业务边界。

### 3.3 数据库路线

**推荐：PostgreSQL 作为首期唯一主数据库。**

理由：

- 财务账本、分录、预算周期、资产事件和导入关系需要事务、约束、唯一键和可审计的关系模型。
- PostgreSQL 的 RLS 可以作为应用层租户过滤之外的第二道隔离边界。
- JSONB 可以保存外部账单的原始字段和映射元数据，同时不破坏统一账本的结构化查询。
- `pgvector` 可以在首期承载家庭独立的 AI 记忆向量，减少独立向量服务的运维面。
- `pg-boss` 可以让异步导入、OCR、内容发布和记忆清理复用数据库基础设施。

数据库使用规则：

1. 应用数据库角色禁止 `BYPASSRLS`；migration 使用单独的受控角色。
2. 每个家庭业务表使用非空 `household_id`，唯一索引和外键优先带上租户维度。
3. 每个 HTTP 请求和后台任务都必须在事务中设置当前家庭上下文，RLS 使用 `current_setting` 校验。
4. 不允许直接把客户端传入的 `household_id` 当成权限来源。
5. 财务金额使用 `numeric`/定点金额类型，禁止使用浮点数作为账本真值。
6. 原始账单文件和中间数据只存对象存储及 staging 表，正式账本只引用规范化来源。

### 3.4 存储与异步任务

#### 对象存储

生产使用腾讯云 COS 私有桶，所有对象键必须包含家庭 ID 或平台发布包命名空间：

```text
households/{household_id}/media/{asset_id}
households/{household_id}/finance-imports/{batch_id}/original
households/{household_id}/finance-imports/{batch_id}/staging
households/{household_id}/ai-memory/{artifact_id}
platform/howtocook/{release_id}/...
```

客户端只获得短时签名地址；签名地址不得写入可长期缓存的页面状态或公共日志。

#### 异步任务

所有任务消息至少包含：`task_id`、`household_id`、`actor_id`、`trace_id`、`idempotency_key`、`task_type` 和 `payload_version`。

首期任务：

- 账单文件扫描、解压、解析、表头探测和 OCR。
- 账单规范化、关联候选和重复识别。
- HowToCook 下载、解析、标准化、审核队列和发布包生成。
- AI 洞察、记忆提取、向量生成和记忆清理。
- 原始导入数据 365 天清理、家庭删除和导出。

任务失败不得直接写入正式账本或确认状态；任务必须支持重试、死信、人工重跑和状态审计。

## 4. 核心领域架构

### 4.1 财务必须是确定性主链路

```text
原始文件
  → SourceRecord
  → TransactionLink / ReconciliationGroup
  → 用户确认
  → LedgerTransaction / LedgerEntry
  → 预算、趋势、资产成本和下钻
```

任何财务首页数字、预算环、趋势线或资产成本点，都只能从正式账本和资产事件生成。AI 可以提供匹配候选和解释，但不能跳过用户确认写入正式账本。

### 4.2 多来源账单的实现顺序

1. 文件识别：文件哈希、编码、压缩包、工作表、PDF 页。
2. 表头扫描：默认前 100 行，支持多行表头和用户指定表头。
3. 字段映射：日期、金额、收支方向、商户、订单号、交易号、账户、备注、币种。
4. 标准化：日期时区、金额符号、商户名称、订单号、退款和转账语义。
5. 候选匹配：订单号强匹配，金额/时间/方向/账户/商户组合匹配，输出置信度和依据。
6. 关系确认：重复、父子结算、退款/冲正、手续费、拆分或无关。
7. 生成统一账本：银行记录作为资金锚点，支付平台记录补充详细信息。
8. 统计和下钻：所有摘要返回可复现的过滤条件和来源 ID。

### 4.3 HowToCook 内容路线

```text
上游最新版
  → 本地快照
  → 解析
  → 标准化
  → 质量门禁
  → 审核队列
  → 可回滚发布包
  → 推荐 / 搜索 / 详情 / 采购清单
```

运行时不访问 GitHub。推荐池、详情内容、搜索索引和采购清单字段均从同一个发布包生成，禁止手工维护多个不一致 JSON 副本。

## 5. AI 网关路线

### 5.1 AI 网关必须做的事

- 从认证会话解析当前家庭和成员。
- 验证该成员对本次 AI 能力和数据类型的权限。
- 只读取当前家庭的连接配置、记忆和业务上下文。
- 对家庭 API Endpoint 做白名单/安全校验、超时、重试和限流。
- 标记模型、规则版本、输入数据范围、用量、结果和降级原因。
- 把建议保存为 `AIInsight` 或 `AIActionProposal`，确认前不能改变正式业务数据。
- 连接失效时回到本地规则和确定性能力，禁止回退到全局默认 AI。

### 5.2 V1.0 协议建议

V1.0 先实现通用 OpenAI 兼容连接配置：

```text
provider_label
endpoint_url
protocol
model
secret_ref
timeout_ms
max_input_tokens
enabled_capabilities
```

协议适配器不写入业务模块。后续增加其它 provider 时，只新增适配器和能力声明，不改家庭隔离、审计和记忆模型。

### 5.3 AI 记忆最小闭环

```text
领域事件
  → 权限过滤
  → 记忆候选
  → 家庭记忆存储
  → 家庭向量命名空间
  → AI 请求上下文
  → 洞察 / 行动建议 / 审计
```

推荐首期只开放结构化事实、行为事件和已确认主题/账务结果的记忆。未经用户确认的 AI 推断必须标记为推断，并设置来源、置信度和撤回状态。

## 6. 腾讯云轻量服务器部署方案

### 6.1 首发部署

推荐使用 Docker Compose，服务最少化：

```text
reverse-proxy
web-api
worker
postgres
```

COS、KMS/Secrets Manager 和备份存储作为外部依赖。开发、测试、生产使用独立环境变量和独立数据桶，禁止共用家庭数据。

### 6.2 备份与恢复

- PostgreSQL：每日全量备份，重要上线前增加手工备份。
- 备份文件加密后上传私有 COS，并保留恢复演练记录。
- 备份和导出必须保留 `household_id` 边界；不能通过导出 SQL 生成跨家庭混合索引。
- 首期至少验证“整库恢复”和“单家庭逻辑导出/删除”两条路径。
- 原始账单到期清理必须同步覆盖主库 staging、COS 原件、备份保留策略和任务记录。

### 6.3 监控与运维

首期必须有：健康检查、数据库连接检查、任务队列堆积、磁盘容量、COS 上传失败、AI 延迟/错误率、导入失败率、跨家庭拒绝计数和 365 天清理任务状态。

日志采用结构化 JSON；禁止记录密码、API 密钥、完整账单原文、完整家庭主题正文和未经必要脱敏的 AI 上下文。

## 7. 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| PostgreSQL + 模块化单体 | 事务、RLS、JSONB、向量和队列集中；运维最少 | 单机资源需要监控，后续需规划扩容 | **首选** |
| MySQL + 应用层租户过滤 | 腾讯云常见，团队上手快 | RLS 能力和复杂审计边界弱，需要更依赖应用代码 | 不作为首期首选 |
| PostgreSQL + Redis + 独立向量库 | 各组件能力强 | 服务数量、备份和串租户风险明显增加 | V1.0 不采用 |
| 微服务 + Kubernetes | 可独立扩容 | 早期团队和单机部署复杂度过高 | 后续规模证明后再评估 |
| Next.js 全栈 | 前后端同仓，开发快 | 任务、文件解析、财务事务和 AI 网关边界容易混杂 | 不作为首期主架构 |

## 8. 必须先完成的技术 Spike

### Spike A：数据库和 RLS

验收：建立两个家庭、同一成员模型和一条跨家庭错误请求；证明 API 查询、后台任务、缓存和导出均不能看到另一家庭；证明应用数据库角色不能绕过 RLS。

### Spike B：账单导入

准备至少以下样本：银行 CSV、支付宝 CSV、微信 CSV、XLSX 多 Sheet、前置说明行、多行表头、PDF 和 ZIP。验收：能展示表头识别行、字段映射、错误行、候选关联和确认前后状态变化。

### Spike C：财务下钻

验收：从净现金流卡、预算环、预算图例、趋势数据点、资产成本点和最近流水进入同一账本过滤结果；任何统计数字都能返回来源 ID。

### Spike D：家庭 AI 连接和记忆

验收：家庭 A/B 配置不同 Endpoint/密钥引用，A 的调用、提示上下文、记忆文件、向量和审计不能被 B 读取；删除 A 记忆后，结构化记录、文件、向量、缓存和任务均进入清理状态。

### Spike E：HowToCook 发布包

验收：下载指定最新版，记录版本/哈希，解析出非空步骤、食材和来源，生成推荐/详情/搜索/采购清单使用的同一发布包，并能回滚上一版本。

## 9. 研发顺序与完成闸门

### 阶段 0：技术基线

- 建仓、分支策略、环境配置、Docker Compose、CI、健康检查。
- 建立用户、家庭、成员、权限和审计骨架。
- 完成 PostgreSQL、迁移、RLS 和事务上下文。

完成闸门：家庭 A/B 隔离测试通过，不能用 `household_id` 越权。

### 阶段 1：家庭空间垂直切片

认证 → 创建家庭 → 发布主题 → 评论 → AI 摘要草稿 → 审计。

完成闸门：成员权限、主题状态、AI 建议和撤销流程可走通。

### 阶段 2：吃什么垂直切片

同步 HowToCook → 本地发布包 → 推荐 → 选择确认 → 菜谱详情 → 采购清单 → 自动饮食事件。

完成闸门：推荐、详情、采购字段来自同一版本；没有步骤的菜谱不能发布。

### 阶段 3：财务垂直切片

上传银行账单 → 表头探测 → 字段映射 → 确认 → 账本 → 预算环/趋势 → 下钻。

完成闸门：所有数字可回溯，导入失败不污染正式账本。

### 阶段 4：多来源关联与 AI

导入银行 + 支付平台 → 候选关联 → 用户确认 → 银行锚点/支付平台详情 → AI 解释与审计。

完成闸门：重复、父子结算、退款和不确定候选不重复统计。

## 10. 当前建议直接定下的决策

1. 数据库首选 PostgreSQL，技术 Spike 通过后进入实现，不再在 MySQL/PostgreSQL 间反复摇摆。
2. 首期采用模块化单体，Worker 可独立部署但不拆业务服务。
3. 财务主链路以确定性账本为唯一真值，AI 仅做建议和解释。
4. AI V1.0 先支持 OpenAI 兼容 Endpoint，provider 通过适配器扩展。
5. 生产原始文件使用 COS 私有存储，密钥使用 KMS/Secrets Manager 或等效密钥管理方案。
6. PWA Service Worker 不缓存家庭业务 API 响应。
7. 不开始全量编码，先完成 Spike A、B、C，确认数据库、导入和下钻这三个不可逆风险。

## 11. 仍需在下一轮确认的单向门

- 腾讯云轻量服务器具体规格、操作系统和磁盘扩容方案。
- PostgreSQL 是与应用同机 Docker 部署，还是使用腾讯云托管数据库；首发默认同机仅适用于预算和低并发基线。
- COS、KMS/Secrets Manager、域名、证书和备份的账户准备状态。
- 首发 AI 协议是否只支持 OpenAI 兼容协议，或同步支持其它协议。
- HowToCook 上游最新版的许可证与素材再分发结论。
