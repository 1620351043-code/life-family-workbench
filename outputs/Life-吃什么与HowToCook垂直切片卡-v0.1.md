## 1. 切片目标

让家庭成员在一个移动端闭环内完成：

```text
看到推荐
  → 选择今天吃什么
  → 打开 HowToCook 菜谱详情
  → 调整份数并查看步骤
  → 生成/勾选采购清单
```

HowToCook 是“吃什么”的子页面和内容执行能力，不新增一级导航，不与“吃什么”形成两个平行产品。

## 2. 本切片范围

### P0 必须打通

1. 吃什么首页：今日推荐、推荐理由、搜索入口、智能搭配入口。
2. 推荐结果：主菜单、备选菜单、家庭偏好/限制提示、选择确认。
3. HowToCook 菜谱详情：封面、评分/耗时、食材、工具、步骤、份数调整、收藏。
4. 采购清单：按已确认菜谱生成，支持勾选、数量展示和回溯来源。
5. 行为自动采集：推荐曝光、打开、确认、开始烹饪、完成采购等事件写入家庭范围历史。

### P1 同一底座配套展示

- 吃过什么：由行为事件自动生成的历史展示，不提供重复手动录入表单。
- 长期习惯：由家庭/用户行为聚合出的偏好展示，并显示“基于哪些行为”及时间范围。
- 搜索菜谱：搜索结果复用同一份 normalized recipe 数据，不建立第二套菜谱来源。

### 不在本切片

- 菜谱内容人工运营后台。
- 外卖、购物平台下单和支付。
- 自动替用户确认菜单或自动写入家庭偏好。
- 独立 HowToCook 一级导航。

## 3. 数据来源与边界

### 3.1 HowToCook 本地数据流水线

使用最新版 HowToCook，在构建/更新阶段下载到本地并解析：

```text
上游仓库固定版本
  → raw Markdown / tips
  → parsed 结构化内容
  → normalized recipe / ingredient / step
  → 租户无关的只读菜谱内容库
```

生产运行时不直接依赖 GitHub 请求；运行时只读取本地解析产物。每次更新必须记录上游版本、解析时间、文件数、失败文件和内容 hash。

### 3.2 家庭隔离

- 菜谱内容可以作为公共只读数据复用。
- 推荐结果、确认记录、历史、习惯、采购清单和 AI 记忆必须带 `household_id`。
- 用户不能加入多个家庭；家庭成员只能读取自己家庭授权范围的数据。
- 行为事件不跨家庭训练或拼接个人记忆；AI 推荐输入只来自当前家庭和当前用户授权范围。

## 4. 建议数据对象

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `recipe` | `id`, `slug`, `title`, `source_version`, `summary`, `duration_minutes` | normalized 菜谱主记录 |
| `recipe_ingredient` | `recipe_id`, `name`, `quantity`, `unit`, `optional` | 可计算采购清单的食材 |
| `recipe_step` | `recipe_id`, `step_no`, `instruction`, `image_ref` | HowToCook 步骤 |
| `food_recommendation` | `household_id`, `user_id`, `recipe_ids`, `reason_refs`, `expires_at` | 推荐结果及来源引用 |
| `food_event` | `household_id`, `user_id`, `recipe_id`, `event_type`, `occurred_at`, `metadata` | 自动历史与习惯的唯一行为来源 |
| `food_preference_profile` | `household_id`, `user_id`, `profile_version`, `signals`, `source_event_ids` | 可解释的长期偏好聚合 |
| `shopping_list` | `household_id`, `created_by`, `source_recipe_ids`, `status` | 由确认菜谱生成的清单 |
| `shopping_list_item` | `list_id`, `ingredient_key`, `display_name`, `quantity`, `unit`, `checked` | 可勾选采购项 |

## 5. 页面与交互规范

### 5.1 吃什么首页

- 首屏先展示推荐，不先展示复杂输入表单。
- 推荐卡片可点击进入菜谱预览；“今天就吃这个”是页面唯一主要动作。
- 搜索、智能搭配、吃过什么、长期习惯作为次级入口，不能抢夺首屏主任务。
- 小兔子作为当前推荐上下文入口：解释“为什么推荐”，提供替换或重新推荐；不打开独立聊天页。
- 推荐加载保留卡片骨架；无结果时提供规则推荐和明确原因；错误时允许重试。

### 5.2 推荐确认

- 用户可以在主菜单和备选菜单之间切换。
- 选择后出现明确确认态，确认动作写入 `food_event`，再进入 HowToCook。
- 推荐理由必须能回溯到行为信号、家庭限制、季节/时段等来源；不能只显示“AI 推荐”。
- AI 只生成建议，不自动替用户确认。

### 5.3 HowToCook 菜谱详情

- 顶部返回“吃什么”，不返回一级导航外的独立 HowToCook。
- 食材、工具、步骤分层展示；步骤按顺序展开，避免一屏塞入过多文本。
- 份数调整即时更新食材数量，并显示更新反馈；不能产生隐形舍入。
- “生成采购清单”固定在底部功能层，始终避让安全区和键盘。
- 进入详情、开始烹饪、完成烹饪均自动记录事件；不要求用户另填“吃过什么”。

### 5.4 采购清单

- 每一项支持 44pt 命中区，勾选有即时状态反馈。
- 展示来源菜谱，点击来源可返回菜谱详情；同名食材按规则合并，同时保留来源。
- 清单写入成功后显示状态和创建时间；失败时保留当前勾选状态并可重试。

## 6. 初步 API 契约

以下是进入 API 设计评审前的初版契约，字段名以最终 OpenAPI 为准：

| 方法 | 路径 | 目的 |
|---|---|---|
| `GET` | `/api/food/recommendations` | 获取当前家庭/用户推荐及来源引用 |
| `POST` | `/api/food/recommendations/{id}/select` | 确认推荐并生成选择事件 |
| `GET` | `/api/food/recipes` | 搜索 normalized 菜谱 |
| `GET` | `/api/food/recipes/{recipeId}` | 获取菜谱详情、食材、工具、步骤 |
| `POST` | `/api/food/recipes/{recipeId}/shopping-list` | 按份数生成采购清单 |
| `GET` | `/api/food/shopping-lists/{listId}` | 读取采购清单及来源 |
| `PATCH` | `/api/food/shopping-lists/{listId}/items/{itemId}` | 更新勾选状态 |
| `GET` | `/api/food/history` | 读取自动采集的吃过什么展示数据 |
| `GET` | `/api/food/preferences` | 读取长期习惯及来源事件 |

所有家庭范围接口必须执行当前家庭权限校验；推荐、历史、习惯和采购清单禁止从客户端传入可覆盖的 `household_id`。

## 7. 状态与异常

| 场景 | 页面反馈 | 可执行动作 |
|---|---|---|
| 推荐加载 | 保留卡片骨架 | 等待或取消 |
| 无法使用 AI | 显示“按你的历史偏好推荐” | 使用规则推荐、重试 AI |
| 菜谱缺少步骤 | 标注内容不完整 | 返回推荐或选择其他菜谱 |
| 份数输入异常 | 阻止提交并解释范围 | 修正份数 |
| 采购清单生成失败 | 保留已选菜谱和份数 | 重试 |
| 家庭权限不足 | 说明当前成员不能执行此动作 | 返回或请求家庭所有者授权 |
| 菜谱数据版本更新 | 显示来源版本 | 重新加载，不静默覆盖用户已确认内容 |
